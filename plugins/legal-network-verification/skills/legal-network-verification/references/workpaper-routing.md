# 工作底稿归档与文件边界

## 两层底稿

### 内部网络核查底稿

内部 Markdown 和配套水印截图用于记录查询过程、条件、逐范围项完成度、结果、同名排除和限制。待登录、待人工验证、访问受限及技术失败必须与已完成结果分开呈现。内部底稿不重复填写查询地点和实际查询人；项目整体内部讨论、复核记录如有，另行归档。

### 正式网络查询记录

正式 DOCX 用于监管检查或项目正式归档，统一填写查询地点、查询人和查询对象身份信息，并由查询律师签名。草稿可以如实显示待登录或待验证；最终 DOCX 只有在 `completion-preview` 返回 `final_ready=true` 时生成。存在 `pending_user_action`、`ready`、`running`、`submit_state=unknown` 或范围项缺失执行记录时必须拒绝最终构建。截图另行保存，正式正文不列截图编号、技术状态码和复核人。

## 用户指定分类

本 Skill 不依赖未随包提供的内部分类标准，也不把推荐目录表述为监管强制分类。

- 用户已指定项目目录、工作底稿索引或机构内部分类规则时，按用户指定规则记录建议归属。
- 用户未指定时，仅使用本文件的两层输出布局，不擅自增加01至14等业务分类。
- 同一截图只保存一份；需要在其他模块引用时使用索引或相对链接，不重复复制。
- 本 Skill 不自动移动、复制或重新分类项目既有文件。

## 默认输出布局

在用户明确指定的网络核查项目目录下，`build` 默认采用两层布局：

```text
<project-root>/
├── 01-内部底稿/
│   ├── network-verification.json
│   ├── <主体名称>网络核查底稿-YYYYMMDD.md
│   └── 截图/
│       └── NQ-*.png
└── 02-正式记录/
    └── 网络查询记录-<项目简称>-YYYYMMDD_草稿.docx
```

多个主体可各生成一份内部 Markdown；同一项目或查询批次汇总生成一份正式 DOCX。正式模式文件名不含“_草稿”。历史项目确需在同一目录输出时，使用 `--layout flat`。

从项目创建起，`prepare` 直接写入 `<project-root>/01-内部底稿/network-verification.json`，水印截图直接写入 `<project-root>/01-内部底稿/截图/`；JSON 的 `screenshot_path` 使用相对 `<project-root>` 的 `01-内部底稿/截图/...`。不为符合本布局移动、复制或覆盖用户输入、原始截图或既有运行文件。

所有生成成果目录必须位于同一 `workpaper_root` 内。内部 Markdown 位于子目录时，截图链接使用从该 Markdown 所在目录到唯一水印截图的相对路径。`artifact-audit` 只接受本次专用的 `01-内部底稿`、`02-正式记录` 目录或一份明确成果文件；它不对图片像素 OCR，图片中的敏感内容须人工视觉确认。

## 原始资料保护

- 不修改、删除、移动、覆盖或重命名用户原始文件。
- 用户模板只读使用，不能原位编辑；随包通用模板同样只作为生成来源。
- 用户提供既有截图时，将其视为原始材料；如需水印，输出到新文件并保留来源说明。若用户明确选择“项目中只保存水印版”，原始截图只允许位于临时目录或用户原始资料区，不以覆盖方式处理。
- 不在客户资料根目录进行递归正文扫描或批量哈希，只读取用户明确指定的文件和最小目录。
- 客户项目材料、截图、运行文件和绝对路径不得进入 GitHub 能力仓库。
